agent-skills · the /sdlc loop

Spec to Shipped

One spec, one approval, then a loop that plans, builds, verifies, reviews and ships every feature on its own branch — stopping only for the decisions that are actually yours.

runs unattended waits for you

01Define once

Everything downstream reads from one file. /spec interviews you — in one batched round, not a trickle — and writes SPEC.md. Nothing else in the loop invents product decisions; if the answer isn't here, the run stops and asks.

The interview/specyou answer

Objective and users · which features · what "done" means · stack and constraints · what it must never do. One round of questions, each with a recommendation attached.

SPEC.mdartifact

Six areas: objective, commands, project structure, code style, testing strategy, and boundaries.

Boundaries are the dial that sets how often you get interrupted. The three tiers — always do, ask first, never do — are read by every later phase as standing answers. Most mid-run questions are spec gaps in disguise; write the decision here once and the loop stops asking. A standing Always: open a draft PR per shipped feature even authorizes the --pr behavior without the flag.

02Split into features

The run derives a feature list from SPEC.md, orders it by dependency, and writes the registry it will work from and report against.

#FeatureBranchBaseDepsStatusPR
1Location resolutionfeat/locationmain—shipped#41 merged
2Event feedfeat/event-feedfeat/location1ready#42 draft
3Visibility scorefeat/visibilityfeat/event-feed2in-progress—

A feature with dependencies branches off its dependency, not off main. Otherwise it can't see code it is specified to build on. That's why the registry tracks base separately from branch — and why the draft PR targets the parent, keeping each diff scoped to one feature's work.

03The gate

You approve the feature list, the order, and the branch topology — once. In auto features this is the only planned stop; individual feature plans are not separately gated, or you are back to stepping by hand. Hedged answers ("looks reasonable") don't count as approval.

04The loop, once per feature

Each feature gets its own branch, plan, and state file, then runs the full phase loop. Every task is test-driven and individually committed, so any point in the run is a clean rollback.

Plan/plantasks/[feature]/plan.md

Vertically sliced tasks — one complete path each, not horizontal layers. Every task carries acceptance criteria and a verification step.

Build/build auto

Per task: failing test → minimum code to pass → full suite → build → commit → mark complete. Staging only that task's files, never git add -A.

Verify/test

Full suite, lint, typecheck, and build from a clean state on the current HEAD. Browser-facing work adds a DevTools pass.

Review/reviewloops back ≤ 3

Five axes — correctness, readability, architecture, security, performance. Critical and Important findings return to Build; Suggestions are the agent's own call.

Simplify/code-simplifyonly if flagged

Behavior-preserving cleanup, run only when review flagged complexity. Tests stay green throughout or the change is reverted.

Ship decision/shiploops back ≤ 2

Three specialists in parallel — code reviewer, security auditor, test engineer — merged into one GO / NO-GO with a mandatory rollback plan. The decision is written; the deploy is never executed.

Draft PR--pryour review

On a GO only: push the branch, open a draft PR against the parent branch, body carrying the ship decision, deferred findings, and merge order. Never marked ready, never merged, never auto-merged.

Each phase runs its command's file, not a summary of it. A slash command expands from what a human types — an agent writing /plan into its own output runs nothing. So /sdlc locates the command file (${CLAUDE_PLUGIN_ROOT}/.claude/commands/plan.md, the project's own copy, or the .toml mirror), reads it whole, and follows it verbatim. That matters because the details a paraphrase drops are the ones worth having: /plan's read-only plan mode and its todo.md output, /spec's confirm-before-proceeding, /review's security and performance sub-skills, /ship's exact decision template. Only three instructions are overridden — a command's own approval gate (phase 3 was it), its "go run /spec first" (that's phase 1), and its "the user re-invokes me" (the state file resumes instead).

05When it stops

This is the part that decides how often the loop interrupts you. It is applied literally, not judged case by case.

Stops and asks

  • Irreversible or outward-facing — anything you can't undo with git revert: migrations, deletions, deploys, payments, auth, secrets, third-party writes
  • Spec gap — a requirement missing or contradictory, where the answer changes what gets built
  • Security — any Critical or High finding
  • Stuck — the same failure survives two distinct fix attempts
  • Scope expansion — a new dependency, a broken contract, files well outside the plan

Decides alone

  • Lint, formatting, typecheck fixes
  • Missing test cases
  • Review Suggestions and Importants inside its own diff
  • Internal renames and extractions
  • Docs, comments, changelog entries
  • Reordering independent tasks
  • Implementation choices the spec doesn't constrain — matching existing patterns, and recording the choice

Never does

  • Delete, skip, or weaken a test to reach green
  • --no-verify, git add -A, force-push
  • Disable type checking or loosen lint rules
  • Merge anything, or mark a PR ready for review
  • Execute a deploy

If green is only reachable through one of these, that is the escalation.

Blocking escalations ask immediately. Irreversible actions, spec gaps, and Critical security findings stop the run then and there, with options and a recommendation.

Everything else batches. Non-blocking questions are logged with the assumption the run proceeded on, and presented together at the next phase boundary. One question set, not a trickle.

06How you find out

An unattended run that hits a decision otherwise waits in a terminal nobody is watching. The sdlc-notify hook binds three events, because they fail differently — a run can block without stopping, and stop without blocking.

EventFires whenCatches
NotificationThe harness needs permission, or the session idlesWaiting on you, regardless of what the run thinks
PostToolUseA state file is writtenAn escalation the moment it's recorded — mid-run, before the agent stops
StopThe agent's turn endsWhy it stopped: blocked, at the gate, finished, or paused

Alerts route through your own command, a Slack-shaped webhook, the desktop notifier, or a terminal bell — whichever is configured first. Two rules keep it from becoming noise you learn to ignore: no run in flight means no notification, and identical state alerts once.

07Coming back to it

Every phase transition is written to disk, so a run survives a closed laptop, a lost session, or a week of other work. /sdlc status is read-only and reconstructs the truth from four sources — the registry, each feature's state file, git, and PR status.

SDLC — SPEC.md — 8 features — base: main — last activity 6 days ago

  #  Feature           Status        Phase       Branch            PR
  1  Location          shipped       —           (merged)          #41 merged
  2  Event feed        ready         DONE        feat/event-feed   #42 draft  ← your review
  3  Visibility score  in-progress   BUILD 4/8   feat/visibility   —
  4  Weather overlay   blocked       BUILD 2/6   feat/weather      —          ← trigger 1
  5  Event detail      deferred      —           —                 —          (waits on 3)

Waiting on you (2)
  • Feature 4 — trigger 1 (secrets): API key. Options: server route / drop / other provider
  • PR #42 — draft, GO verdict, waiting for review

Resume point: feature 3, BUILD phase, task 4 of 7
Budgets: review 1/3 · fix attempts 0/2 · consecutive blocked 1
Drift: registry says feature 1 is `ready`, but feat/location merged into main 5 days ago
Warning: main has advanced 14 commits since feat/visibility branched

The reconciliation is the feature, not the table. The registry is what the loop believes; git is what happened. Those diverge the moment you merge a PR yourself. And that last warning matters more than it looks: feature 3's tests passed against a baseline that no longer exists, so its green isn't evidence until base is merged in.

09What it extends

If you already run /build auto, you have most of this. Its Build phase is /build auto — phase 4 reads build.md and runs it with auto as its argument, so the task loop isn't reimplemented or summarized, it's the same file. What /sdlc adds sits entirely outside that loop: a phase before it, four after it, a branch around it, and a state file underneath it.

/build auto/sdlc auto features
Starts fromAn existing SPEC.md — stops and tells you to run /spec if there isn't oneNothing. It runs the /spec interview and writes SPEC.md first
Unit of workOne flat task list, tasks/plan.mdOne feature — its own branch, plan, and state file
Where it runsThe current branchA branch per feature, based on its dependency, not on main
Ends atThe last task's commit, plus an end-of-run summaryA written GO/NO-GO with a rollback plan, and a draft PR per feature
When it stopsAny blocker halts the runBlocking asks halt; the rest is batched, and a blocked feature parks so the others keep moving
LimitsNone declared — a failure it can't fix escalates3 review cycles · 2 fix attempts · 2 ship attempts · 2 consecutive blocked features
ResumingRe-invoke; it picks up at the next unchecked task/sdlc status rebuilds the board from the registry, state files, git, and PR status

Unchanged from /build auto

  • One gate per unit of work. Present the plan, wait for an unambiguous yes, then run. "Looks reasonable" is not approval in either command.
  • Test-driven per task. Failing test, minimum code, full suite, build, commit — the autonomy removes the human between tasks, never the verification inside one.
  • One commit per task, staging only that task's files. Never git add -A, so any point in the run is a clean rollback.
  • Stop on anything irreversible — secrets, migrations, payments, deploys, anything git revert can't undo.
  • The spec is the only source of product decisions. A gap in it is a question for you, not something to invent.

Where the extension actually is

  • Before: the interview that produces the spec /build auto requires but won't write.
  • After: verify, review, simplify, ship — four phases with failure modes /build auto has no way to notice. A Critical review finding and a NO-GO verdict are real stop conditions, and neither exists in a build-only run.
  • Around: the outer loop. Branch per feature, dependency ordering, draft PR per GO — so eight features are eight reviewable diffs, not one.
  • Underneath: a state file. /build auto resumes from checkbox state; /sdlc records the phase, the budgets spent, the decisions taken, and every open escalation — which is also what the notification hook reads.

The honest boundary: /build auto is still the right call for one plan on one branch that you'll review yourself. Feature branches, a registry, and per-feature state files buy nothing there — they're overhead you'd be maintaining for a run that ends in an hour. Reach for /sdlc when the spec has several features that each deserve their own diff, or when the run has to survive you closing the laptop. /sdlc auto without features is the middle setting: /build auto's scope on the current branch, plus the verify, review and ship tail.

10Installing it

/sdlc is a command file plus an optional hook — no runtime, no dependencies. How you install it depends on how the target repo already gets its skills.

Into a repo that already uses agent-skills

The fastest path is to copy the command in. The skills it invokes are already there, so nothing else has to change.

cp .claude/commands/sdlc.md    <target>/.claude/commands/

# other harnesses, if the repo drives them too
cp .gemini/commands/sdlc.toml  <target>/.gemini/commands/
cp commands/sdlc.toml          <target>/commands/

Take the right copy of the command. The body invokes skills by name, and whether those names need the plugin prefix depends on how the skills were installed.

How the skills got thereCopyBecause
Plugin install .claude/commands/sdlc.md It calls agent-skills:planning-and-task-breakdown — the prefix resolves against the installed plugin
npx skills add commands/sdlc.toml Skills land loose, not under a plugin namespace. Save that mirror's prompt body as .claude/commands/sdlc.md — it uses bare skill names

The whole plugin

If the repo has no agent-skills yet, install the plugin and /sdlc arrives with everything else — the 24 skills, the other eight commands, the hooks.

/plugin marketplace add addyosmani/agent-skills
/plugin install agent-skills@addy-agent-skills

Installing from a fork takes one extra edit. .claude-plugin/marketplace.json declares each plugin's source.repo, and that field names the upstream repository. Add a fork as a marketplace without changing it and the install resolves back to upstream — you get agent-skills, silently without whatever the fork added.

Trying it first

A local plugin directory skips the marketplace entirely — no manifest edit, nothing installed globally, and the command disappears when you close the session.

git clone https://github.com/addyosmani/agent-skills
claude --plugin-dir /path/to/agent-skills

Verify any of the three with /sdlc status. It is read-only and safe in a repo with no run in progress — it should report that there's nothing to resume rather than erroring.

Notifications are a separate step

The hook that pages you at an escalation is opt-in, so installing the plugin doesn't start notifying every project. Copy hooks/sdlc-notify.sh into the repo and wire it to three events in .claude/settings.json:

{
  "hooks": {
    "Notification": [
      { "hooks": [{ "type": "command", "command": "bash \"${CLAUDE_PROJECT_DIR}/hooks/sdlc-notify.sh\"" }] }
    ],
    "Stop": [
      { "hooks": [{ "type": "command", "command": "bash \"${CLAUDE_PROJECT_DIR}/hooks/sdlc-notify.sh\"" }] }
    ],
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [{ "type": "command", "command": "bash \"${CLAUDE_PROJECT_DIR}/hooks/sdlc-notify.sh\"" }]
      }
    ]
  }
}

With no channel configured it falls back to a terminal bell. SDLC_NOTIFY_WEBHOOK sends Slack-shaped JSON; SDLC_NOTIFY_CMD pipes the message to anything you like. Either way every notification is appended to .claude/sdlc-notify.log, which is what you read after an overnight run.

What autonomy does not change. Every task still earns a failing test first, a passing test after, its own commit, and a review pass. The loop removes the human between phases — never the verification inside them.

A loop that runs unattended and skips tests isn't faster. It just moves the discovery of the bug to production.
